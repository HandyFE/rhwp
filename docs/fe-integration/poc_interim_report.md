# rhwp 적용 POC 중간 결과 보고 (rhwp editor · rhwp converter)

- 작성일: 2026-10-29 (중간 보고. 최종 보고서·발표 자료의 바탕이 되는 초안)
- 대상: 핸디 전자결재(FeWebClient 기안기, BMS 서버)에 rhwp 를 적용하는 두 가지 POC
- 저장소: `rhwp-FE`(엔진·WAR), `FeWebClient_rhwp` 브랜치 `poc/rhwp-editor`(기안기), BMS trunk 작업본(미커밋)
- 세부 근거 문서는 모두 `rhwp-FE/docs/fe-integration/` 에 있다(§8).

## 1. 한 장 요약

| POC | 목표 | 현재 결과 | 제품 포함 판정(중간) |
|---|---|---|---|
| **rhwp editor** — 기안기용 에디터 | 웹한글 에디터 자리에 rhwp 를 넣어 기안·결재가 되는지 확인 | 개발 서버에서 **기안기 로딩과 결재올림(상신) 성공**. 그러나 상신된 본문이 구조적으로 깨져 저장됨(E3), 미지원 API·액션 20여 종, 저장·안 추가·그림·인쇄가 비어 있음 | **지금은 불가, 중장기 과제.** 50~75인일 추가 개발과 한컴 정답 자료가 있어야 판단 가능. 단기 적용 대상 아님 |
| **rhwp converter** — 서버용 문서편집 | BMS 가 한컴 문서변환서버·hwplib 대신 rhwp 로 결재 본문에 서명·관인·값을 넣게 함 | `rhwp.war` + 워커 풀 구현, BMS `DocConverter` 16종 중 13종 대응, Tomcat HTTP·장애·동시성 시험 통과, 샌드박스 실문서 88건 게이트에서 결함 4종 발견·1종 수정 | **조건부 가능.** 웹한글 HWP + 1단계 표 서식은 지금도 됨. HWPX·중첩 표·글자 사이 표 문단은 미해결. 대체 경로(hwplib)와 자기 검증(verify)이 있어 단계적 투입은 가능 |

공통 결론: rhwp 는 **읽기·렌더링은 제품 수준**, **저장(직렬화)은 우리 서식에서 결함이 계속 나오는 영역**이다. 서버 용도는 "저장 뒤 다시 열어 확인하고, 다르면 기존 방식으로 넘기는" 운영 설계로 결함을 가둘 수 있지만, 편집기 용도는 사용자가 만든 문서가 그대로 저장돼야 하므로 같은 방법으로 가둘 수 없다.

## 2. rhwp 란

- **무엇**: Rust 로 만든 오픈소스 HWP/HWPX 엔진(원작 edwardkim/rhwp, MIT). 파서·직렬화기·조판·렌더러(CanvasKit/SVG)·편집 커맨드를 갖추고, 같은 코드가 **네이티브 CLI**(Windows/Linux 단일 실행 파일)와 **WASM**(브라우저)으로 빌드된다. 브라우저 에디터 rhwp-studio, Chrome/Edge/Firefox 확장, VS Code 확장, npm 패키지(`@rhwp/core`)가 같은 엔진 위에 있다.
- **우리가 쓰는 것**: 회사 포크 `rhwp-FE`(원작 v0.8.7 기준, 당분간 원작에 PR 하지 않음). 포크에는 웹한글컨트롤 API 호환 층 `npm/hwpctrl-ocx`(`@rhwp/hwpctrl`, 원장 484항목 중 339 완료)가 있다.
- **규모·활동**: Rust 테스트 약 10,500개, PR 마다 fmt·clippy·전체 테스트·WASM 빌드·속성 기반 왕복 테스트, 파서 퍼징 8종. 최근 30일 커밋 851건, 작성자 16명, 약 한 달 간격 릴리스. 0.x 버전이라 변경 속도가 매우 빠르다.
- **공개된 검증 수치**: 서울시 결재문서 HWPX 18,365건 IR 왕복 99.81%, 일반 문서 10,000건 자기 왕복 "실질 저장 결함 0". 단, 이 수치는 **rhwp 가 자기 파서로 다시 읽은 판정**이고 한글(한컴)에서 실제로 열리는지를 전수 확인한 공개 수치는 없다.
- **우리 관점의 강점**: 설치 없는 브라우저 편집, 서버 측 무UI 처리, 한 엔진으로 클라이언트·서버 공용, 문서 객체가 스레드 안전해 워커 풀 구성이 가능, 악성·손상 파일 자원 상한(압축 256MiB, 재귀 64 등).
- **우리 관점의 약점**: 누름틀(필드) 직렬화가 결함이 계속 나오는 영역(6월 이후 수정 커밋 약 35건), 저장 경로 퍼징 없음, 하위 호환 정책 문서 없음, 동봉 글꼴 일부(Happiness Sans·카페24) 상용 번들 전 라이선스 검토 필요.

## 4. rhwp editor POC 결과

### 4.1 구조

기안기 `FeEditorFactory` 가 `FeRhwpEditor`(웹한글 에디터 상속)를 만들고, 같은 출처 iframe 에 rhwp-studio(`chrome=embed`)를 띄운 뒤 `@rhwp/hwpctrl` 플러그인을 `hwpCtrl` 로 넘긴다. 결재 로직은 웹한글용 코드를 그대로 쓰고, 웹한글 JS API 와 호환 층(COM 규격)의 차이는 FE 브리지(`rhwpCtrlBridge.js`)가 임시로 흡수한다. 켜기는 `feEditor=rhwp` 또는 `localStorage fe.editor=rhwp`.

### 4.2 확인한 것

| 항목 | 결과 |
|---|---|
| 로컬 시험 페이지 | `Open` → 필드 목록·값 넣기·읽기 → 화면 표시 정상 |
| 기안기 빌드 | webpack·eslint·prettier 통과 |
| 개발 서버 기안 | **기안기 로딩, 통합서식 blank 로 결재올림 성공**(2026-10-29). 도중 멈춘 곳(첫 `Open` 거절, 콜백 미호출, 미지원 API 예외, realm 차이) 5건은 플러그인·브리지에서 처리 |
| 상신 본문 검사 | BMS 샌드박스에서 그 문서를 꺼내 바이트로 확인: **문단 0 이 깨져 있음**. 입력한 글자가 구역 정의 앞에, 안내 문구가 단 정의 앞에 있고 누름틀은 비어 있다(E3). 원인 두 가지가 겹침 — 누름틀 밖 입력이 막히지 않음(E2), 저장 때 글자·컨트롤 순서 재계산이 무너짐(저장 결함 2 계열) |

### 4.3 비어 있는 것

- **미지원 액션 6/13**: ViewZoom, ParagraphShape, AllReplace, CellBorder, InsertHyperlink, TablePropertyDialog.
- **미지원 API**: MoveToFieldEx, 툴바·리본·상태줄 제어, ShowCaret, ScrollPosInfo, CreatePageImageEx(쪽 이미지), ViewProperties·IsModified 대입, **InsertPicture**(로고·심볼·서명·관인·본문 그림 모두 실패).
- **범위 밖이던 것**: 저장·상신 경로(웹한글은 서버 업로드 후 URL, 호환 층은 바이트), 안 추가·이동·복사·본문 삽입(`GetTextFile(JSON,saveblock)`→`SetTextFile/Insert`), 서명·관인 그림, 인쇄·PDF, 배포용 저장.
- **품질**: 누름틀 안내문(`"본문을 입력하세요.;"` 형식) 미인식으로 안내문이 값으로 저장·인쇄됨(E1), 양식 편집 모드 없음(E2), 편집·액션이 studio 트랜잭션 밖에서 실행돼 undo·재조판 누락 가능(D2·D3), studio 메뉴가 그대로 노출(D5), 임베드 빌드 41MB·글꼴 404·WASM MIME(D6~D8).

### 4.4 판정: 제품 포함 가능 여부

**지금은 불가.** 이유는 세 층이다.

1. **저장 정합성** — 사용자가 편집한 문서를 rhwp 가 저장하면 우리 서식에서 구조가 깨진다(E3, 결함 1·2·3·4). 서버 용도와 달리 편집기는 "다시 열어 확인하고 실패하면 다른 엔진으로" 가둘 수 없다. 저장 경로 전반(문단 안 글자·컨트롤 위치 재계산)을 고치고 운영 서식 전체로 회귀 게이트를 통과해야 한다.
2. **기능 공백** — 서명·관인 그림, 안 추가·이동·복사, 인쇄·PDF, 저장 업로드가 없다. 결재 업무의 핵심 흐름이라 "일부 기능만 rhwp" 로 갈 수 없다. 견적 50~75인일(확신도 낮음~중간)이며 블록 직렬화(C3)가 가장 불확실하다.
3. **정답 자료 부재** — 누름틀 command 형식·양식 모드 같은 의미는 공개 스펙에 없어 한글(한컴) 산출물과 비교해야만 확정된다. 요청 자료(`rhwp editor.md` 요청 표)가 아직 없다.

해결 불가능한 것은 없다. 다만 **"웹한글 대체"는 엔진 결함 수정 + 호환 층 보강 + FE 수정 + 전체 시나리오 검증을 모두 끝내야 효과가 나는 묶음 과제**라서 단기 과제로는 맞지 않고, 서버 컨버터를 먼저 안정화해 저장 경로 신뢰를 쌓은 뒤 재평가하는 것이 맞다.

## 5. rhwp converter POC 결과

### 5.1 구조

```
BMS (Java 8, Spring)                       rhwp.war (같은 Tomcat 또는 전용 WAS)
 RhwpConverterService(DocConverter) ──HTTP multipart──▶ ConvertServlet/FieldsServlet
   ├ CellAction 16종 → actions JSON              │  WorkerPool(K개, 대기·시간 상한·재기동)
   ├ 서명 이미지 URL → 바이트 첨부                │    └ rhwp worker (stdin/stdout NDJSON, 문서는 경로)
   ├ 실패 → hwplib 등 대체 구현체                 │        convert / fields / values, 저장 후 재적재 verify
   └ 연속 실패 → 서킷 브레이커(5분)                └ /health
```

### 5.2 구현한 것 (1단계 + 2·3단계 W1~W8)

| 영역 | 내용 |
|---|---|
| 액션 | `insertTextEx`·`insertSignTextEx`·`insertSignDateTextEx`(셀 전체 비우고 글자+글꼴), `appendTextEx`·`appendSign*`(문단 추가), `insertText`(누름틀 값·글꼴 유지), `insertImage`·`appendPicture`(셀 크기 맞춤 그림). `addPageCell`(을지 병합)과 조회 2종은 별도(조회는 `/fields`·`/field-values`) |
| 안정성 | 요청마다 panic 격리, 저장 후 **재적재 검증**(필드 목록·본문 구조·쪽수·셀 글자·그림 수·누름틀 값) 불일치면 `ok:false` + 출력 삭제, 워커 시간 초과 강제 종료·교체, 밖에서 죽은 워커 교체 |
| 엔진 수정 | 저장 결함 1(누름틀 끝 표시 순서)·2(표 뒤 누름틀 값 위치)·4(여러 문단 누름틀 끝 표시 소실) 수정, 셀 안 컨트롤 삭제·셀 그림 삽입 API 추가 |
| BMS 쪽 | `RhwpConverterService` + 팩토리 분기 + 설정 키(url·token·fallback·breaker·verify). 커밋하지 않음 |
| 배포 | Linux Dockerfile(gnu/musl), 설정은 `-Drhwp.*`·환경변수·web.xml |

### 5.5 판정: 제품 포함 가능 여부

**조건부 가능 — 단계적 투입.**

- **지금 바로 되는 범위**: 웹한글이 만든 HWP 본문, 결재 표가 1단계 표인 서식, 글자 서명(이름·날짜·대결/전결)과 셀 서명 이미지. 샌드박스 70건 중 이 범위의 서명 시나리오는 모두 통과했다. 대체 경로와 verify 가 있어 결함이 있어도 문서를 망가뜨리지 않고 기존 방식으로 넘어간다.
- **투입 전 반드시**: ① 운영 서식·실문서 회귀 게이트 상시화와 한글 열기 확인, ② Linux 빌드·메모리·처리 시간 실측으로 워커 수·타임아웃 결정, ③ BMS 개발 서버에서 기안→결재→접수→반려와 대체 경로·브레이커 동작 확인, ④ 한컴 변환기 산출물과 그림 크기·위치·날짜 형식 대조(완료 문서의 서명은 `MM/DD` 줄 위, 이름 아래 형식).
- **부족한 것(개발 필요)**: HWPX 저장 경로(결함 6)와 HWPX 구조 검증 도구, 중첩 표 깊이 N, 결함 3 위치 모델 재작성, 결함 5 분석, 여러 문단 필드 값 조회, 관인 배경 그림 방식(HsCell 방식 서식이 있으면), 을지 병합(사용 여부 확인 뒤).
- **해결 불가 요소는 없다.** 가장 큰 위험은 "저장 직렬화 결함이 계속 나온다"는 성질 자체이며, 이것은 자기 검증 + 대체 경로 + 버전 고정 + 회귀 게이트로 운영 위험을 가두는 방식으로 대응한다. 운영 WAS 가 자식 프로세스 실행을 막으면 전용 WAS 로 분리 배치한다.

## 6. 두 POC 의 공통 교훈

1. **검증 도구가 결함을 찾는다.** 자기 파서 재적재(verify)만으로는 결함 4 처럼 조용한 손상을 놓친다. 바이트 수준 컨트롤 순서 비교(`ctrlorder.py`)가 잡았다. HWPX 에도 같은 도구가 필요하다.
2. **실문서가 빈 서식보다 많이 알려 준다.** 빈 서식 7종은 전부 통과했지만, 결재 진행 중 실문서 88건에서 결함 4종이 나왔다. 샌드박스 자료 선별 도구(`pick_sandbox_docs.py`, `Hc20Decode.java`)를 만들어 두었다.
3. **본문 형식이 생각보다 다양하다.** 웹한글 HWP 외에 웹한글 HWPX, 데스크톱 한글 HWPX/HWP(HC20 포장), 한컴 변환기 저장본이 섞여 있다. 제품 범위를 "어떤 본문 형식을 지원하는가"로 명시해야 한다.
4. **한컴 정답 자료 없이는 의미를 확정할 수 없다.** 누름틀 안내문 형식, 그림 배치, 서명 날짜 형식은 공개 스펙 밖이다.
