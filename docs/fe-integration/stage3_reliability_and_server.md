# rhwp 제품 적용 신뢰성 평가와 BMS 서버 운영 방식 검토

- 일자: 2026-10-28
- 기준 source: rhwp-FE v0.8.7 (`1a76570e8`, 2026-10-06 업스트림 main 미러)
- 선행 자료: [1단계](stage1_verification.md), [2단계](stage2_api_scope.md)
- 성격: 평가 보고. 코드를 고치지 않았다. 측정은 개발 PC(Windows 11)에서 했고 리눅스 서버 측정은 아직 없다.

3. 실패 시 대체 경로(사람 처리 또는 기존 방식)를 남겨 두는 운영 설계

## 2. 근거

### 2.1 우리 서식으로 직접 확인한 것

FE 서식 16종(통합서식 8종, FE `res` 6종, 첨부 본문 2건)에 대해 두 가지를 실행했다.
- (a) 모든 필드에 글자 채우기
- (b) 모든 셀 필드에 그림 넣기

그 뒤 HWP로 저장해 다시 열고, 원본과 개체 순서를 비교했다(증적 `output/pr-review/fe-stage1/formsweep/`).

| 대상 | 열기 | 필드 채우기 | 저장 후 구조 |
|---|---|---|---|
| FE `res` 서식 6종, 첨부 본문 | 정상 | 정상 | 정상(개체 순서 동일) |
| 통합서식 `blank1`·`blank3`·`fixedrecv` | 정상 | 정상 | **결함 1**: 누름틀 끝이 결재 표 뒤로 밀림 (글자·그림 모두) |
| 통합서식 `3to4`·`5to6` | 정상 | **결함 2** | 결함 1 (그림 넣을 때) |
| 통합서식 `1page`·`audit` | 정상 | **결함 2** | 정상 |
| 통합서식 `linked` | 정상 | 정상 | 정상 |

- **결함 1**: 누름틀 끝 표시가 뒤 개체 뒤로 밀린다. 한글에서 결재 표가 사라지거나 `본문` 누름틀에 묶인다. 한글에서 직접 확인했다(1단계 §7).
- **결함 2**: 문단이 표로 시작하고 바로 뒤에 `본문` 누름틀이 오면, 채운 값이 누름틀 **밖**(문단 맨 앞)에 쓰인다. 다시 열면 `본문` 값이 빈 값이다. 저장 직전까지는 값이 맞게 보이므로, **저장 단계에서 값이 엉뚱한 곳으로 옮겨지는 데이터 손상**이다.

```text
tonghap_1page 원본  [secd][cold][tbl][%clk 시작]1[clk 끝][문단끝]
값 채워 저장        [secd]본문값테스트[cold][tbl][%clk 시작][clk 끝][문단끝]
```

- 두 결함 모두 `src/serializer/body_text.rs` `serialize_para_text()` 에서 생긴다. 문단 안에서 "앞쪽 개체 + 누름틀 + 뒤쪽 개체"가 섞여 있을 때 글자·개체의 순서를 다시 계산하는 부분이다.
- 변경하지 않은 문단은 원본을 그대로 쓰므로 문제가 없다. **편집한 문단에서만** 생긴다.
- rhwp 자체 왕복 검사(`exportHwpVerify`, 자기 재파싱)와 저장 손실 보고(`contentLoss`)는 이 결함을 잡지 못한다. 결함 2는 다시 열었을 때 필드 값을 비교해야 보인다.

### 2.2 프로젝트의 신뢰성 근거 (저장소 조사)

강점:
- 테스트 약 10,500개(Rust). PR마다 fmt·clippy·전체 테스트·WASM 빌드·속성 기반 왕복 테스트가 CI에서 돈다.
- 파서 퍼징 8종(매일), CodeQL 정적 분석.
- 코퍼스 규모 검증이 있다.
  - 서울시 결재문서 HWPX 18,365건 IR 왕복 99.81% (2026-06)
  - 일반 문서 10,000건 자기 왕복 "실질 저장 결함 0" (2026-07)
- 입력 자원 상한(압축 해제 256MiB, XML 256MB, 재귀 깊이 64 등)이 있다. 악성·손상 파일 방어선이 있다는 뜻이다.
- 스레드 안전성: 문서 객체가 `Send`(스레드 간 이동 가능)라 워커 풀 구성이 가능하다. 전역 가변 상태는 없다.
- 라이선스 MIT. 동봉 폰트 일부(Happiness Sans, 카페24)는 상용 번들 전에 별도 검토가 필요하다.
- 활발함: 최근 30일 커밋 851건, 작성자 16명, 약 한 달 간격으로 릴리스.

약점(제품 적용 관점):
- **대규모 "통과" 수치 대부분이 rhwp 자기 판정**(자기 파서로 다시 읽기)이다. 한글에서 실제로 열리는지를 전수로 확인한 공개 수치는 없다. 한글 COM으로 확인하는 도구(`tools/loadsave_sweep/`, `tools/hwp_open_bisect/`)는 있으나 수동 실행이고 CI에 연결돼 있지 않다.
- 누름틀 직렬화는 6월 이후 수정 커밋이 약 35건 있는 **결함이 계속 나오는 영역**이다. 위 결함 2종도 아직 업스트림에 수정 기록이 없다.
- 저장 경로 퍼징 타깃이 없다(파서만 있음).
- 0.x 버전이고 변경 속도가 매우 빠르다(90일 커밋 6,500건). 공식 하위 호환 정책 문서가 없다. 그래서 **버전을 고정하고 우리 쪽 회귀 게이트를 따로 둬야** 한다.
- 오류 처리: CLI `batch` 는 문서별로 panic을 격리하지만 `mcp-serve` 에는 격리가 없다. WASM은 panic 시 인스턴스를 버려야 한다.

### 2.3 제품 적용을 위한 최소 체계 (권고)

1. **버전 고정**: 포크에서 검증한 커밋만 배포한다. 업스트림 동기화는 게이트를 통과한 뒤에만 한다.
2. **우리 서식 회귀 게이트**(자동, 업그레이드마다 실행):
   - 운영 서식 전체에 대해 필드 채우기·서명·관인 → 저장 → 다시 열어 값·개체 순서·쪽수를 비교한다(이번 [`scripts/formsweep.mjs`](scripts/formsweep.mjs) 를 정식화).
   - 정기적으로 Windows + 한글에서 산출물을 열어 확인한다(`tools/loadsave_sweep` 활용).
3. **운영 중 자기 검증**: 저장할 때마다 다시 열어 넣은 값이 그대로인지 확인한다. 다르면 실패로 처리하고 대체 경로로 넘긴다. 결함 2 같은 무증상 손상을 운영에서 막는 장치다.

## 3. BMS 서버 운영 방식

### 3.1 호출 비용 실측 (개발 PC, Windows 11, release 빌드)

입력: 통합서식 blank(3)(55필드, 1쪽, 약 25KB). 30회 반복.

| 방식 | p50 | p95 | 비고 |
|---|---|---|---|
| CLI를 요청마다 실행 (`edit fill-fields` 16필드) | 31.7ms | 37.4ms | 프로세스 생성 포함 |
| ㄴ 프로세스 기동만 (`--version`) | 19.4ms | 44.3ms | Windows 기준. 리눅스는 보통 이보다 훨씬 짧다 |
| 상주 프로세스(Node + WASM)에서 처리 | 26.6ms | 47.0ms | 열기 8.6 + 필드 16개 6.7 + 그림 1개 7.1 + 저장 2.6 |
| WASM 초기화(상주 시 1회) | 48.6ms | — | 상주 메모리 약 185MB(Node 포함) |

참고: 큰 문서(10MB, 20쪽)는 CLI `info`(쪽 나누기 포함) 1회에 약 140ms가 걸렸다.

해석:
- 결재 서식처럼 작은 문서는 **처리 시간 자체가 수십 ms**다. 프로세스 생성 비용은 요청당 약 20ms 수준이라, 하루 수천~수만 건이면 요청마다 프로세스를 띄워도 감당할 수 있는 규모다.
- 진짜 부담은 **동시 요청이 몰릴 때의 프로세스 수 관리**와 **JVM에서 자식 프로세스를 다루는 운영 복잡도**다. 상주 방식은 이를 정리하려고 쓰는 것이다.

### 3.2 운영 방식 후보

| 방식 | 구성 | 장점 | 단점 | 추가 개발 |
|---|---|---|---|---|
| A. 요청마다 CLI 실행 | Java `ProcessBuilder` → `rhwp edit … --json` | 가장 단순. 요청 사이 완전 격리(크래시·메모리 누수가 JVM에 안 옴). 바이너리 1개 | 요청당 프로세스. 동시성 상한을 Java 쪽에서 관리해야 함. 셀 필드 그림 CLI가 없음 | 셀 그림 CLI 2~3일 |
| B. **Rust 상주 HTTP 서비스** (권장) | rhwp 라이브러리를 직접 링크한 작은 서버(`rhwp-server`). BMS가 내부망 HTTP로 호출 | 단일 바이너리, Node 불필요. 스레드 풀 + 요청별 `catch_unwind` 격리. 가장 빠름. systemd·Docker 운영 쉬움. 헬스체크·메트릭 넣기 쉬움 | 새 서비스 코드 작성·유지 | 4~6일 (API 3~4종: 필드 채우기, 필드명으로 그림, PDF, 검증 포함) |
| C. Node + WASM 상주 서비스 | Node HTTP 서버 + `@rhwp/core`(또는 `@rhwp/hwpctrl` 웹한글식 API) | **지금 바로** 셀 그림까지 된다(1단계에서 확인). 웹한글식 호출(`PutFieldText`, `InsertPicture`) 재사용 가능 | 서버에 Node 런타임 추가. WASM panic 시 인스턴스 재생성 필요. 메모리 더 씀 | 2~4일 |
| D. `rhwp batch` / `mcp-serve` 상주 (stdio) | Java가 자식 프로세스를 띄워 두고 stdin/stdout으로 요청 | 이미 있는 기능 | `batch` 는 축이 고정(fill 등)이고 그림 삽입이 없음. `mcp-serve` 는 단일 클라이언트, panic 격리 없음, 세션 도구에 그림 없음 | 그림·격리 보강 필요 → 비권장 |
| E. JNI / Java FFM 직접 호출 | Rust를 공유 라이브러리로 JVM에 적재 | 호출 비용 최소 | 네이티브 크래시가 **BMS JVM 전체를 죽임**. 현재 C ABI는 텍스트 추출 4개 함수뿐 | 큼 → 비권장 |

### 3.3 권고

- **운영 방식은 B(Rust 상주 HTTP 서비스)** 를 권한다.
  - BMS는 기존처럼 HTTP로 호출하면 되고, 서버에는 바이너리 하나만 둔다.
  - 요청별 panic 격리, 타임아웃, 동시성 제한, 헬스체크를 서비스 안에 둘 수 있다.
  - §2.3의 "저장 후 다시 열어 값 확인"도 서비스 안에 넣는다.
- 빠르게 시제품이 필요하면 C(Node + WASM)로 먼저 검증한 뒤 B로 옮기는 방법도 있다. 이 경우 같은 엔진을 쓰므로 결과가 같다.
- 처리량이 작고(예: 분당 수십 건 이하) 운영을 최소화하려면 A도 실용적이다. 격리 면에서는 A가 가장 안전하다.

### 3.4 결정에 필요한 정보

1. BMS에서 예상되는 처리량(하루 건수, 최대 동시 요청)과 응답 시간 요구
2. BMS 서버 OS·배포 방식(리눅스 배포판, Docker 사용 여부), Node 런타임 설치 가능 여부
3. 실패 시 대체 경로(재시도, 사람 처리, 기존 방식)를 둘 수 있는지
4. 운영 서식 목록 — 회귀 게이트 대상으로 쓸 실제 서식 전체
